Requirements Fit Analyzer · Process map

How the Requirements Fit Analyzer works.

A system that reads requirement documents and measures how well each one fits a verified record of my work. Its first job is my own career search. Every night it finds open roles and judges each one against my record. I decide where to apply, AI selects verified statements for each application, and every call and every edit I make flows back into the next night and the next draft.

The map

Seven phases in one loop.

Scripts do everything that has one right answer. AI reads and writes only where the words matter, and only after passing a bar I wrote down first. I make the calls and supply the ground truth. Select a phase to open its detail. Each number matches a note below the map.

How to read this map

  • Script. Code that gives the same answer every time.
  • AI judgment. A model reading or writing language.
  • Me. The calls only I can make, and the ground truth.
  • Gate. A check the work must pass to move on.
  • Note. Explained in the numbered list below the figure.
  • Feedback. Results flowing back to improve an earlier phase.
  1. Find. Every night a script pulls each employer’s own job board and fetches the full text of every new posting. I choose which employers are on the list. (employers’ own hiring-system feeds across 13 platforms, stored in DuckDB)
  2. Judge. Rules, trained models and a small embedding model score each posting. Two AI judges read the Required block of the shortlist. (rule engine; TF-IDF with logistic regression; BGE sentence embeddings; TypeSafe Jev and Gemma 4)
  3. Validate. Every judge is scored against my own blind grades and keeps only the role its score earned. (employer-grouped cross-validated AUC; catch and agreement rates; measurement system analysis)
  4. Decide. I make the calls: build, pass or hold. Grades I give before seeing any machine score become the answer key the judges are scored on.
  5. Build. AI selects verified statements, word for word, from a database of my work and drafts the letter. Scripts check every fact and phrase, then build the Word files. I edit and send. (spaCy keyword extraction; Claude with written skills; python-docx export and its exact reverse)
  6. Learn. My calls retrain the models through a gate. A script finds every edit I make to a sent document and AI explains why, so the voice guide and the record of my work both improve. (gated retraining; word-level document diff)
  7. Publish. A snapshot of each night rebuilds the reports, charts and presentation. I review anything new before it goes public. (PostgreSQL reporting views; SVG charts; an HTML deck)

The guardrail ring. The scripted checks every phase passes through: the gate a retrained model must clear, each judge’s accuracy bar, the repeatability bars an AI judge passes before it may act, the guards on every statement, the check on opening verbs, and the check on every finished document.

Detail 1 of 5 · Phases 1, 2 and 7

The nightly run.

One run finds every open role, scores it, and rebuilds the reports before I look at them. Scripts run it from start to finish, and the two AI steps come near the end and read only the shortlist.

  1. Wake on schedule. I pick the start time. A scheduled task wakes the laptop five minutes before it, so a sleeping machine still runs, and the pre-flight checks run twice: when I confirm and when it starts. (a Windows scheduled task with wake-to-run, since a sleeping laptop never fires cron)
  2. Apply my calls. The build, pass and hold calls and the grades I entered during the day wait in a queue. They are applied first, so tonight’s scores already know them.
  3. Retrain the models. When a retrain is due, the fit models train again on my latest calls and grades. A new model replaces the old one only if it clears the gate: a shuffled-label check for leaks, accuracy no worse than the last model that passed, and no drop in labels. A model that fails is discarded, and every attempt is logged. (shuffled-label AUC must land between 0.40 and 0.60; employer-grouped AUC at least the last promoted run’s minus 0.02; labels at least 95% of the last run’s)
  4. Pull every job board. A script pulls each employer’s own job board, the same data its careers page shows. New postings are added and returning ones reopened. A posting is closed only when a clean, complete pull no longer lists it, and nothing is deleted, so every posting keeps its full history. (one adapter per hiring-system platform, run in parallel)
  5. Fetch the posting text. The full text of each new posting is fetched, along with a share of the older ones still missing it. A posting fetched again keeps the grade it already has.
  6. Screen by rules. Rules screen each posting on function, level, location, clearance and discipline. Every verdict keeps its reasons, so when a rule changes, the postings it screened out can be reopened.
  7. Score with trained models. Small trained models score fit on my three lenses: process, technical and applied AI. The best of the three sets the rank. Two more score the Required block and the closest matches, and their scores are shown beside the rank. (TF-IDF on words and word pairs with class-balanced logistic regression, one model per lens; employer-grouped held-out AUC about 0.955. The Required score adds a stacked logistic regression over TF-IDF, a BGE-base embedding of the Required block and a per-line roll-up)
  8. Match requirements to my record. A small embedding model that runs on the laptop matches each requirement in the posting to the piece of my record that answers it, and marks it strong, partial or a gap. As a ranker it scored 0.669 against the trained models’ 0.955, so its job is to explain the rank. (BAAI bge-small-en-v1.5 sentence embeddings, cosine similarity, run locally)
  9. AI review of the shortlist. Jev, TypeSafe AI’s model for fast typed decisions, reads the Required block of each posting on the shortlist. A clear fail is demoted. A fail that rests only on grey lines comes to me to check. A posting I have already ruled on is never judged again: my call outranks Jev’s. (typed outputs, one pinned model version; scored on the gold set at 91% catch and 93% agreement)
  10. Second read of the demotions. Gemma, a second AI judge, reads only Jev’s demotions. It never passed its accuracy bar in eight rounds, so its read is shown as evidence beside each demotion and decides nothing. (Gemma 4 through Google AI Studio; bars of 70% catch and 85% agreement)
  11. Apply my calls again. Calls I made while the run was going are applied before the snapshot, so nothing I decided waits a day.
  12. Snapshot the night. One snapshot copies the night’s results into the reporting database in a single swap, so a report never reads a half-finished night. (DuckDB to PostgreSQL in one transaction)
  13. Rebuild reports and charts. Forty-five seconds later the reports, charts, workbook and presentation rebuild from the snapshot, and my application tracker refreshes. If nothing changed, nothing rebuilds. The public charts show only industries and percentages. (SQL reporting views feed SVG charts, an Excel workbook and an HTML deck)

Why a script here, and judgment there.

Pulling boards, screening, training and scoring models, and rebuilding reports each have one right answer, so code does them the same way every night. AI reads only where the words matter: the Required block of a shortlisted posting, after the trained models have ranked it. Two of the eleven nightly stages call a language model, both near the end.

What I do: pick when the run starts, choose the employers on the list, and make my calls in the app during the day. The grey cases wait for me when the run finishes.

On scoring nights the run also scores the AI judges against my blind grades. That part is in Judges and validation.

Detail 2 of 5 · Phase 3

Every judge is a gauge.

Rules, trained models, an embedding model, two AI judges and I are each scored against my blind grades. Each keeps only the role its score earned. A check mark means the judge passed its bar; a cross means it missed and kept a smaller role.

  1. My blind grades. Grades I give a posting before I see any machine score. Only these count as the answer key, and every judge below is scored against them. (the gold set: blind rows that include a Required-fit call)
  2. Rules. Rules on function, level, location, clearance and discipline. Each verdict keeps its reasons, so a rule that screens out a good posting can be found and changed.
  3. Trained models. Small models trained on my own calls and grades, one per lens. They rank well on employers they never saw in training, and a retrain replaces them only if it passes the gate. (TF-IDF with logistic regression; AUC measured on held-out employers; retrain gate with a shuffled-label leak check)
  4. Embedding model. Matching requirements to my record by meaning looked like the obvious ranker. Its scores bunched too tightly to rank, so it failed that bar and kept the job of explaining the rank. (bge-small sentence embeddings, cosine similarity)
  5. Gemma. A second AI judge for the Required block. It missed its bar in eight rounds, so it decides nothing and its read is shown beside Jev’s demotions. (Gemma 4; bars of 70% catch (the share of my fails it also catches) and 85% agreement)
  6. Jev. TypeSafe AI’s typed-decision model passed the Required bar and a repeatability study, so it may demote a clear fail. It missed the calibration bar, so it acts only on its yes-or-no call and hands grey cases to me. (measurement system analysis: lens agreement at least 0.70, repeat flips at most 2% (it scored 1.6%), median change at most 0.03, prompt injection caught 4 of 5 times; calibration ECE bar 0.10, missed)
  7. Me. I am a gauge too. Between my first pass on one blind sheet and my final grades, 55 of 72 grades stayed the same, which tells me how firm the answer key is. (test-retest repeatability of the human grader)

Why measure the judges.

In a Six Sigma project I would never trust a gauge I hadn’t measured against a known standard, for accuracy and for repeatability, with the bar written down before the test. The same rule applies to every model here, and to me. When a judge misses its bar, it keeps a smaller role, and the bar stays where it was.

What I do: grade postings blind, before I see any machine score. Those grades are the standard every judge is measured against, and my own re-grades measure me.

The AI judges are scored on their own nights: Gemma and Jev on the answer key, plus repeat runs and planted prompt injections for Jev. Every retrain is scored as it runs.

Detail 3 of 5 · Phase 4

My calls feed the next night.

I record build, pass and hold calls and blind grades in a small app. They wait in a queue and are applied before the next run, where they become training labels and the answer key. The tracker runs beside it.

  1. My calls in the app. In a small app I mark a posting build, pass or hold, with a reason and any requirement I don’t meet. An ordinary pass teaches the models. A pass for reasons outside the work, such as location, does not. (a Python desktop app writing to a PostgreSQL queue)
  2. Grades only. I can grade a posting without deciding on it: a grade on each lens, an overall grade, and whether I meet the Required block. Given blind, these become answer-key rows.
  3. Blind grading sheets. Batches of postings I grade with every machine score hidden. Some include decoys, to measure the AI judges directly. They go straight to the answer key.
  4. Decision queue. Everything I enter waits in one queue, so nothing I decide during the day is lost while the pipeline is busy.
  5. Applied before the run. The queue is applied at the start of each run and again just before the snapshot. A grade that conflicts with an earlier blind or seen call of mine is refused, so blind and seen grades never mix in the answer key.
  6. Training labels. Decisions and lens grades become the labels the next retrain learns from. A build on a posting Jev demoted is a human overrule: Jev never judges it again, and it becomes a ruling Jev is scored on.
  7. The answer key. Blind grades with a Required call join the gold set every judge is scored against.
  8. Status, notes, contacts. Beside the calls, the tracker keeps where each application stands, my notes and the people involved. I update it from the app or a command line.
  9. Email watcher. Every hour a script reads job email, such as confirmations and rejections, and updates the tracker.
  10. Tracker database. One database stores the tracker, the record of my work and the nightly snapshot. (PostgreSQL)
  11. Tracker sheet and reports. A read-only sheet and my daily focus report refresh from it, so I never keep two lists.

Why a queue.

My calls arrive at any hour, and the pipeline is often busy. A queue means nothing I decide is lost or half applied, and the order never changes: my calls first, then the scores.

What I do: every build, pass and hold call, every blind grade, and the status of every application. The email watcher handles the confirmations and rejections.

Detail 4 of 5 · Phase 5

Select the facts, then check every one.

AI selects verified statements word for word and drafts the letter. Scripts check every fact and phrase, build the Word files, and read my edits back after I send, so the next draft starts closer to how I write.

  1. I choose to build. A role from the reports gets a build only when I choose it. A duplicate check runs first, then the application gets its own folder and a line in my tracker.
  2. Capture the posting. The posting text is saved word for word, so the draft is written against what the employer actually asked for, even after the posting comes down.
  3. Sort the keywords. The posting’s keywords are sorted into required, preferred and context, so the draft can be checked for coverage later. A language library finds the candidates and an AI model sorts them. (spaCy, then Gemma 4, with Groq and then a Claude subagent as fallbacks)
  4. Read the requirements. Claude reads the requirements against my background and the rules on what I may claim, notes where I fit and where I don’t, and asks me anything it can’t settle from the record. (Claude with written skills, my voice guide and a guardrails file)
  5. Select statements. Claude picks 14 to 16 statements from the database of verified statements about my work. Each is used word for word, and a script looks up each one’s guards: what it must never be used to claim, and which statements it may not appear beside. (202 statements, each tagged by project, problem solved and lens)
  6. Draft the resume and letter. Claude writes the summary and the cover letter in my voice, and lists every statement it cut and why. The facts come only from the selected statements.
  7. Check coverage. A script measures how much of the posting’s keyword list the draft covers. Covering most of it is the target; chasing every last keyword makes worse writing, so the check stops there. (65 to 75% is the target band)
  8. Quality check. A script checks everything with one right answer: every figure against the statement it came from, company names and dates against the record, standing bans on certain figures, layout rules, the letter’s parts, and my voice. One failure stops the build until it is fixed. (a voice checker counts the phrasing habits of AI-written text, measured against my own pre-AI writing)
  9. Build the Word files. Scripts turn the checked draft into a resume on my template, fitted to two pages, and a one-page letter that matches it. (python-docx; Word itself counts the pages)
  10. Check the Word files. The same check runs on the Word files, and the letter must read back identical to its draft.
  11. I edit and send. I read both documents, edit them in Word, save the PDFs and send the application.
  12. Record the send. The tracker records the application, and the PDFs move off the laptop to cloud storage.
  13. Find every edit. A script compares the documents I sent with the drafts and records every change, down to a single word. A script never misses a one-word cut. (a word-level diff of the sent Word files against the drafts)
  14. Explain each edit. Claude writes why I made each change. Meaning is a judgment, so this step is AI, and it feeds the voice guide.
  15. Read the Word files back. Scripts turn my sent Word files back into the draft format, exactly, so the record of the application matches what I actually sent. (exact inverses of the export, tested lossless on 36 of 40 earlier letters, the rest off only by trailing spaces)
  16. Check again. The quality check runs once more. A failure here is usually an edit I made on purpose, so it is reported to me and never “fixed.”
  17. New statements: I decide. Edits that changed a statement come to me as candidates. I decide in the database itself whether the master statement changes; tailored wording never leaks back on its own.

Why the facts are selected, word for word.

A resume is a list of claims, and a claim has one right answer: what happened. So the facts are selected word for word from statements I have already verified, and a script checks each figure against its source. AI does the parts that take judgment: reading the posting, choosing what fits, and writing the summary and letter around the facts.

What I do: choose to build, answer the questions, edit both documents, send, and decide whether any edit changes a master statement.

Detail 5 of 5 · Phase 6

Four loops that learn from me.

The models learn from my calls, the judges from my blind grades, the voice guide from my edits, and the record of my work from the statements I approve. Each loop has a gate, so nothing changes just by drifting.

  1. Models. My build and pass calls and lens grades become labels. The models retrain, and a new model replaces the old one only if it beats it under the same gate, so a bad retrain can never demote a good model. (labels per lens; shuffled-label leak check; employer-grouped AUC; every run ledgered)
  2. Judges. Each new blind grade, and each time I overrule a demotion, adds to the answer key. On scoring nights every AI judge is scored again, and a judge keeps only the role its bar allows. A newer model version takes the same test before the pipeline moves to it. (catch and agreement bars; repeatability, injection and calibration studies; results ledgered)
  3. Voice. Every edit I make to a sent resume or letter is found by script and explained by AI. After about five applications the voice guide is re-derived from the explained edits, and any habit that can be counted goes into the voice checker, so drafts drift less from how I write. (word-level diff; an edits corpus; countable tics move into the deterministic checker)
  4. Statements. When an edit changes a statement, or a build surfaces background the record lacks, it becomes a candidate. Only I change a master statement, in the database itself, so tailored wording never leaks back into the record on its own. (lint views check length, references, first person, tags and opening-verb variety)

Why every loop starts with me.

Each loop starts from something only I can supply: a call, a blind grade, an edit, a fact about my own work. Scripts move the signal, and the gates decide what changes.

What I do: keep making calls, grading blind and editing what I send. The loops do the rest.

A fifth, smaller loop: when a rule screens out a good posting, its stored reasons show which rule to change, and the posting reopens.

The split

Who does what, phase by phase.

The thread through the whole map: select instead of generate where the facts matter, script anything with one right answer, and grade the graders, me included.

Phase Scripts AI judgment Me Why the split
1 Find Board pulls, opening and closing postings, posting text, the wake task None Choose the employers on the list Same input, same answer, every night.
2 Judge Rules, trained models, embeddings, the rank Two AI judges read the Required block None Models rank; AI reads where the words matter.
3 Validate The retraining gate, accuracy and repeatability bars, the logs None Blind grades, the ground truth A judge is a gauge, and gauges get measured.
4 Decide The queue, applying it, tracker updates, the snapshot None Build, pass or hold; blind grades; Required calls Only I know what I want and what I meet.
5 Build Intake, posting capture, guard lookups, coverage, quality checks, Word export and its reverse Reading the requirements, choosing statements, the summary and letter Review, edit, send Facts are selected word for word; prose is drafted, then checked.

7 Publish Reporting views, charts, the presentation, the reports None Review anything new before it goes public Numbers are computed, never typed.

How this map was made

Drawing the map found the gaps.

I drew this map by tracing the process against the code, step by step. The trace found seven places where the process I described and the process that ran had drifted apart: a voice check no step called, mechanical checks I ran by hand, a cover letter with no Word export and no way back, edits that became lessons only when someone remembered to look, a grading app that couldn’t add to the answer key, documentation that described an older flow, and exports renamed by hand. I closed each one before drawing, so the map shows the process as it runs today.

Most of the system was built before the Leland AI Builder program. During the program I added the voice checks and the reporting charts and presentation.
