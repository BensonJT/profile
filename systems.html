Forester

Process modeling software · product, not publicly launched

2025 – present

Situation
Process models drive redesigns and cost cases, but most are drawn by hand as pictures.
Obstacle
Hand-drawn models are usually wrong and nobody can tell: two people describe the same handoff differently, inputs appear from nowhere, and at scale no reviewer can hold the whole graph in mind.
Action
Built software that captures a process as data, using my decomposition and ICOM method, and draws every diagram from it. A Coach finds contradictions across the model, ranks the fixes, and can complete a missing flow in one click.
Result
One model produces 6 diagram languages and 35 metrics across 6 stakeholder lenses. Phase 1 is feature-complete and in use on a live client engagement.

Builder’s notes

How I built this
Problem
The method only scaled as far as I could. For 30+ years my process work ran on one method: decompose the work, then at every step capture who supplies and receives what, the inputs, controls, outputs, and mechanisms, and the time and value in each step.
Approach
Capture the model once and compute every diagram from it. Forester is a web app: a React and TypeScript workspace, a FastAPI backend, and Postgres. You build the process as a tree, edit it as a tree, a spreadsheet, or one step at a time, and every diagram and metric is computed from that single model: flow efficiency, rolled throughput yield, sigma level, Cp and Cpk, required staffing, equipment effectiveness, and the cost of poor quality.
Key decisions
Store each arrow once.
  • One data model. Each input, control, output, or mechanism arrow is stored once, and is at the same time an edge in every diagram and an input to the metric roll-ups.
  • Every metric written twice and checked. Each formula exists in TypeScript for the screen and Python for the server, locked to shared test fixtures so the two can’t drift, and governed by one canonical metric catalog.
  • One owner for every fact. Each kind of fact, from the database schema to the roadmap, has exactly one document that owns it, and a change to the code updates its owner in the same commit.
What went wrong
Real client work found what demo models didn’t. The first paying engagement modeled in Forester exposed that the order of steps in the BPMN export was inferred from the tree rather than declared.
Next
The interview is still ahead. The feature that matters most, an AI interviewer that runs the conversation I used to run by hand and captures the model as it goes, isn’t built yet.

How I built this
Problem
The job boards were showing me jobs that had already closed. My first attempt, in March 2026, pulled from job aggregator APIs. The matches were mostly postings that had closed weeks earlier, and on one run every aggregator link I followed returned an error.
Approach
Read the source, then narrow it in stages. On September 15, 2026 I started over. The new pipeline pulls the same data each employer’s careers page uses, across 27 hiring-system platforms, into a single DuckDB file.
Key decisions
Treat every AI model like a gauge that has to earn trust.
  • Deterministic first, AI last. The free steps do the volume work.
  • Distill, don’t prompt-tune. I had 362 good matches and only 7 audited near misses, and nothing can be tuned reliably against 7 examples.
  • An AI judge is an appraiser. Before Jev could demote anything, it went through a measurement-system study against my blind grades: it caught 91% of what I caught, agreed 93% of the time, and flipped an answer on a repeat question 1.6% of the time against a 2% bar.
What went wrong
Some of the smartest-looking parts failed their own tests. Matching requirements with embeddings looked like the obvious ranker. It wasn’t: similarity scores bunched so tightly that it reached an AUC of 0.669 against the fit model’s 0.955.
Next
Close the loop on every disagreement. Next is turning each place Jev and I disagree into a recorded ruling, then re-measuring Jev against them.
What is automated

Three triggers: a clock, a launch button, and a conversation. The judgment about where to apply stays with me.

Scheduled: daily sweep
Every morning a cron job sweeps the faith-based job boards and refreshes one report, archiving a dated copy only on days something changed.
Started by hand, then hands-off
I start the full pipeline from a menu, now or at a set time (the laptop wakes itself). From there it runs unattended: it retrains the ranking models on my new labels and promotes one only if it passes its gate, sweeps more than 150 company job boards, fetches each job description, splits it into requirements, screens and scores my fit, has a second model review the shortlist and demote weak matches, scores both models against a human-graded gold set when the rules change, and writes a ranked Top Jobs page. Boards that fail three runs in a row are flagged at the top of that page.
Triggered: the package build
When Claude and I have talked through my fit and picked among several roles, the build decision starts a tailored resume and cover letter from my resume database and voice guides. Nothing is sent without my review.
Triggered: tracker
Every write to the application tracker refreshes a Google Sheet copy. The database is backed up nightly, with an hourly standby copy.

Why not fully scheduled: a full run with a retrain and gold scoring takes hours of laptop time, so I start it when the machine is free.

Builder’s notes

How I built this
Problem
The research lived in many places, each read by hand. The investor’s research ran across separate data services, spreadsheets, and broker exports, each opened and read by hand.
Approach
Model the process first, then build the system around it. Before any code, I modeled the client’s operating process in Forester. Its five top-level activities, from the overnight batch to the investor’s own routine, became the architecture’s top-level decomposition word for word, and every component exists to serve one of them.
Key decisions
AI explains the numbers but never computes them.
  • A never-AI zone. Price math, technical analysis, money flow, and reconciliation are deterministic code only.
  • Free hosted models, chosen by test. The news is read by Gemma 4, an open-weight model, on Google AI Studio’s free tier.
  • Fetch and compute are separate. Ingest scripts only fetch; every calculation pulls the stored data in its own script, and everything derived recomputes whenever the data underneath it moves.
What went wrong
The quiet failures were the dangerous ones. On the client’s machine, blocked network calls degraded runs without stopping them, so for a stretch no overnight run finished and nobody heard about it.
Next
Make every failure visible before the first overnight run. The alert rules came after the silent stretch. Starting again, they would exist before the system ran unattended for the first time.
What is automated

Meridian runs on two clocks: a news lane three times a day, and an overnight batch I schedule. Every step is safe to rerun, so a missed or skipped slot loses nothing.

Scheduled: news lane
Three times a day. It pulls news and options data for every active ticker, scores the new articles with a language model (newest first), and derives events against the market calendar. It checks the data vendor’s remaining credits first; when the free tier runs low, it skips the pull but still scores the backlog.
On my schedule: overnight batch
I pick a start time and the laptop wakes itself to run the batch, which finishes before the market opens. It pre-flights twice: once when I confirm, so a problem shows up before I go to bed, and again at the start time.
Triggered
Checks that fire from a calendar of known releases, and a file import that routes each file by type or stops with an error.
Guardrails
Locks keep the news lane from colliding with the batch: if the batch is running, the news slot stands down and the next one catches up.

Why not daily: the batch would run every night if my hardware allowed it. On the client’s machine it does.

Situation

Obstacle

Builder’s notes

How I built this
Problem
A row count says the migration worked. The exercise: compare a legacy claims system’s output with a new system’s before cutting over, find the discrepancies, and size their impact.
Approach
A pipeline that treats every field as a quality opportunity. I built it with Claude Code from February 9 to 12, 2026: Python and DuckDB, ingesting ten CMS synthetic claims files in 10,000-row chunks, checking the loaded totals against the source files, transforming in SQL, and comparing the two systems field by field across 4.7 million claim records and 343,803 beneficiary records.
Key decisions
Measure it like a process, report it like a decision.
  • Each field compared is an opportunity for a defect, so data quality comes out as defects per million, yield, and sigma level, field by field and rolled up: 4.56σ for claims and 4.67σ for beneficiaries.
  • The scorecard puts the sigma levels beside the counts that matter for go/no-go: 7 of 13 claim fields below 4.0σ, 4,777 claims the source never had, 159 beneficiary IDs lost and 159 new ones, and 82,699 payment discrepancies.
What went wrong
The deck needed corrected figures. Figures in the presentation deck were wrong and were corrected in June, after the original submission.
Next
Lead with what blocks the cutover. A sigma level near 4.6 looks good. The missing claims are what actually decide go/no-go, so they belong first on the page, with the sigma levels as context.

How I built this
Problem

Approach
The program is the product. The method’s content lives in one source file. Product management, applied to a spreadsheet.

  • Verified in the real engines. The build opens the Excel file in real Excel, recalculates, and checks for repairs, errors, and circular references; Google computes the Sheet.

What is automated

The code is the source of truth. One command builds the current workbook from the latest code, checks it, and keeps the user guide in step with it.

Triggered: the build
On demand, the generator builds the workbook as an Excel file and as a native Google Sheet. The Excel build is recalculated in real Excel and scanned for error values, and both are checked against a worked example’s 134-value answer key. Triggered: the user guide
With one flag, a build that passes its checks also regenerates the user guide: tab purposes, columns, dropdowns, conditions, blueprints and commands come from the same model as the workbook, and every tab’s screenshot is retaken from the verified example. Turns any Google Sheet or Excel workbook into living documentation: a report, a self-describing DuckDB database, a JSON file, and a context file an AI assistant can answer questions from. Public code at github.com/BensonJT/sheets_decomposer (MIT license).

How to use
./sd ingest <file or Sheets URL> runs the extraction. ./sd query runs SQL against the result, and ./sd sample builds the practice workbook and its answer key.
Inputs
A Google Sheets link (OAuth, service account, or a link-shared export with no credentials) or an .xlsx file.
Outputs
report.md, gem_context.md, model.duckdb (18 commented tables and 13 views), and model.json.
Stack
Python 3.11, DuckDB, openpyxl, networkx, the Google Sheets and Docs APIs, and a Gemini Gem for questions.
Privacy
The Gem’s context file contains structure, labels, and formulas, not data rows, unless sample values are explicitly requested.

Known limit: a formula that is consistent but computes the wrong thing looks clean. The report is where a human review starts, not where it ends.

Builder’s notes

How I built this
Problem
Capable tools that start every session from zero. AI tools are good at the work and forget everything between sessions. Each one knew different things, facts I gave in a chat drifted from the facts I gave in the next, and I kept making the same corrections.
Approach
Standard work, written where the work happens. I solved it the way process work always has: document the work at the point of use, keep one source of truth, check it, and improve it continuously.
Key decisions
Facts kept apart, and checked by code.
  • Ground truth is separate from what the tools learn. Facts about my record live in one place that every procedure points to, never copied into each step, so a correction is made once.
  • Every file says what AI may do to it: edit freely, only add, or only read.
  • Code does the mechanical work; the model does the judgment. The repository holds 100+ deterministic scripts, each built for one job: pulling and verifying Scripture, rendering slides and video, narrating audio, uploading media, exporting resumes.
  • Scripts also check what Claude writes. An audit script holds every skill to Anthropic’s authoring guidance, and a fact guard fails any rewording pass that drops a number, date or path.
What went wrong
The manual drifted, the way manuals do. Facts piled up in Claude’s own memory, close to 200 notes, and some disagreed with the vault.
Next
The same pattern, for a team. I would start with one router per domain and a single instruction file on day one, instead of growing into them.
What is automated

Keystone keeps itself in sync, and its skills make other automation one request away.

Scheduled: vault sync
Every ten minutes, each machine pulls, commits and pushes the vault. Every change is in Git, so any file can roll back, and both machines start from the same context. Config files that live outside any repo ride along.
On demand
The skill and context system lets one request start a wide range of work: a job package, a lesson asset, an email cleanup. An audit script checks the skills against the standard, and a fact guard confirms a rewording pass dropped no facts.

Why it matters: the automations in the other projects depend on this. Every skill they run lives here.

Structure
Markdown in git, organized by projects, areas, resources and archive, with a system folder for personas, skills, lessons learned and the index.

This site, built the same way
Problem
A résumé lists results. It doesn’t show the work. I wanted a site that shows how I work, not just what I achieved, and I wanted to build it with AI without it reading like AI wrote it.
Approach
A hand-built static site, written with Claude. HTML on GitHub Pages: one stylesheet, one script, self-hosted fonts, no framework. As of November 12, 2026: 51 pages, including 33 articles.
Key decisions
Every number traced to what I actually did.
  • The site’s value is that it’s true. When a figure didn’t match the record, it changed to the record, and an honesty callout in my own voice is on the about and résumé pages.
  • One stylesheet governs every page, with named color and type values and text colors checked for contrast, and nothing styled inline.
  • Real diagrams over decoration. AI-made images and an AI infographic were retired in favor of a domain map and process diagrams, and em dashes came out of the prose.
What went wrong
The drafts claimed more than I did. A $2.8B figure became the $455M portfolio I actually governed. A 450% claim was removed. A 10% year-over-year claim was replaced with the actual ranges.
Next
Check each figure as it’s written. The corrections came in a concentrated pass after pages were already live. Checking every number against the record as it’s drafted would have kept the wrong ones from ever publishing.
