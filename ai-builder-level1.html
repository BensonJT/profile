Build 01Shipped

Design System Skill

A skill that applies my profile site’s exact colors, type, and layout rules to anything I build.

Builds on: my profile site’s design

01 · The problem

A look described in words drifts.

I wanted everything I build in this program to feel like my profile site. Telling an AI “warm, editorial, gold accents” gets you something close, and close is the problem: every page comes back a slightly different shade of the same idea.

02 · The approach

I pulled the values from the site’s code.

Instead of describing the site from screenshots, I gave Claude access to the site’s source and had it read the one stylesheet that governs every page. Out came a design guide with exact hex codes, the type scale, the layout rules, and five words for the feel: editorial, grounded, confident, understated, crafted.

I turned that guide into a reusable skill, /personal-profile-design, so any future build can load the whole visual system with one command.

03 · Key decisions

One source of truth, referenced everywhere.

Reading the code mattered because the site already had decisions a screenshot can’t show, like separate gold tones for text on light and dark backgrounds, each checked for contrast. An eyeballed palette would have lost that.

I also kept every copy pointing back to the original. This portfolio uses an exact copy of the profile site’s stylesheet rather than a rewrite, and the write-up skill I built next loads this skill instead of repeating its colors. Same principle as any process standard: copies drift, references don’t.

04 · What went wrong

My first portfolio looked like someone else’s.

Before this skill existed, the first version of this portfolio was a dark theme with neon accents and an animated network background. Side by side with my profile site, it read as a different person, and a more junior one. I scrapped it and rebuilt the portfolio on the profile site’s system.

05 · What I’d change

Put the skill under version control.

The skill lives in my Claude account, where it works in both the Claude app and Claude Code. Next I’ll keep a copy in my own git-tracked workspace, so changes to it have a history like everything else I build.

Applies my profile site’s visual identity to any page, portfolio, artifact, or mockup, using the site’s exact values.

How to use
Type /personal-profile-design in Claude or Claude Code, then describe what to build. It can also load on its own when a request asks for something in this style.
Inputs
A request for a page or design. Optionally, existing content to restyle.
What it provides
A token block of colors, type sizes, and spacing to paste first; color and typography rules; the alternating-band page layout; specs for cards, tiles, buttons, and links; a pre-finish checklist; and a one-paragraph style prompt for handing the look to another tool.
Outputs
Markup and CSS that match the profile site.
Works with
/personal-profile-writeup, which loads this skill before writing build write-ups for this portfolio.

Known limit: the skill holds a snapshot of the site’s values. If the profile site’s stylesheet changes, the skill has to be updated by hand, or the two will quietly drift apart.

Standalone pages load the fonts from Google Fonts. This portfolio and the profile site host their own copies instead.

Build 02Shipped

Portfolio Website

This portfolio: a living record of the program, built to match my main profile site and merged into it in October 2026.

Builds on: my profile site

01 · The problem

The course wanted one page. I needed something that would last.

The program asks for a portfolio as a single self-contained HTML file. That works for a class, but I already have a profile site, and a second site that looks and works differently splits my story in two. I wanted one page that could grow through the course and then move into the profile site without being rebuilt.

02 · The approach

Version two mirrors the profile site, file for file.

Version one followed the course prompt: a single dark-themed file with an animated background. Once I compared it with my profile site, I rebuilt it on the profile site’s own system instead.

The page now uses the same folder layout as the profile repo, an exact copy of its stylesheet and script, the same self-hosted fonts, and the same headshot at the same path. The handful of new pieces, like the build cards and the popups, live in their own small stylesheet and script, written to be appended to the shared ones at merge time.

03 · Key decisions

Design for the merge from the start.

Every choice was made against one test: will this drop into the profile site unchanged? That’s why the page is named ai-builder.html rather than index.html, which the profile site already uses. Write-ups live in the page next to their card, not inside a script, so they can become detail pages later.

The course still needs a single file, so that became a build step, not the source. A short Python script packs the page, styles, scripts, fonts, and images into one file for upload, and the multi-file version stays the one I edit.

My workspace commits and pushes to git every ten minutes, so the API key for publishing lives in a file git is told to ignore, checked before the key went in.

04 · What went wrong

A fix that never landed.

I tightened the popup spacing, saw it work in testing, and moved on. Two steps later, the popups still looked loose. The save to my folder had run at the same moment as the edit and copied the old stylesheet. It was caught by opening the popups again and checking the built file for the rule, not by assuming the save had worked.

05 · What I’d change

Decide where it ends up before building the first version.

Knowing from the start that this page would merge into my profile site would have skipped a full rebuild. The single-file version is now live on the course site; still to do is merging the page into the profile site when the program ends.

A portfolio page for the Leland AI Builder program: every course build, documented as it ships, alongside the systems I’ve built since December 2025. Built to merge into my profile site.

Files
ai-builder.html (the page), css/site.css and js/site.js (exact copies from the profile site), css/builder.css and js/builder.js (page-only pieces), fonts/, img/.
Update a build
Run /personal-profile-writeup and name the build. It writes both popups, sets the card’s status, and updates the project notes.

Restyled and published as a single file on the Leland course site. Merging into the profile site is next.

Links to the profile site are full web addresses until the merge, when they switch to relative paths.

Build 03Shipped

Voice Guide Skill

Two guides to how I write, built from nearly 30 years of my writing from before AI, tested blind, and loaded by every writing skill in my AI workspace.

Builds on: Keystone’s voice and persona files

01 · The problem

My recent email would have taught Claude to sound like Claude.

The course builds a voice guide from your 20 most recent sent emails. I have written with AI every day since December 2025, and no email from before that survives. I also noticed I had started picking up some of Claude’s words myself. A guide built from my inbox would have described the AI, not me.

02 · The approach

I built the guide from what I wrote before AI.

I gathered my own writing from 1995 to 2023: personal journals (about 231,000 words), letters to friends, a 2011 email to a director, career and accomplishment notes, and study notes. I added 71,000 words of my own typed messages to Claude for my current habits. Claude analyzed it into the course’s nine sections, and every example in the guide is a verbatim quote checked against the source.

I split it into two guides, professional and personal. The same person writes a status update and a condolence letter, but not at the same speed. Then I tested the guides blind and wired them into my AI workspace.

03 · Key decisions

The older writing wins, and a blind test decides.

When my recent writing and my pre-AI writing disagree, the guide trusts the pre-AI writing. My 1995 to 2011 letters and journals show how I use a word. My 2026 chats can hand Claude’s habits back to it.

I didn’t trust the guide until it beat no guide. Fresh Claude agents drafted the same reply to a message I had received, two with the guide and two without, and I rated the shuffled drafts before learning which was which. A small script checks the countable rules (em dashes, banned phrases, ending on a question). I judge the rest.

I didn’t make it a standalone skill. The guides live in Keystone’s persona files, the master index lists them, and each writing router (job applications, cover letters, professional posts, Bible study posts) tells Claude to load them. Any writing task picks them up without my asking. Most rules ask Claude to vary its words, not ban them: I like how Claude puts things, and the goal is drafts that sound more like me with each document.

04 · What went wrong

The first version lost to no guide at all.

In round 1, drafts written with the guide scored 2.5 out of 5 on average. Drafts without it scored 4.0. The guide’s own descriptive words leaked into the drafts (“plainly”, a word I almost never use). The task instructions leaked too: “honest” showed up in all four drafts. And numbered lists came from my chats with Claude, where I write instructions, not from how I write to people.

I added a “how to use this guide” section: my own words come first and the guide only adjusts them, never copy the guide’s words, and tell a story in paragraphs. In round 2, the guide plus my own words scored 5.0, the guide alone 4.0, and no guide 3.0. In round 3 the context already held my words and every fact, and every arm scored 4.5 to 5. A guide matters most when the context is thin.

05 · What I’d change

Test it where it should matter most.

The next tests use thin-context tasks, like a cold email or a resume summary, where Claude has little of my wording to borrow. The guide also keeps learning. When I send a document, the version I sent is compared with Claude’s draft and every sentence I changed is saved. After about five documents, I’ll rewrite the guide’s sentence rules from those edits.

Two guides to how I write, professional and personal, that Claude loads before drafting anything in my voice. A checker and a growing file of my edits keep them improving.

How to use
Ask for any draft in my voice. Claude finds the right guide through the index and the writing router for the task. Give it my notes or a rough draft first. It builds from my words and uses the guide to adjust. Then run python3 voice_check.py draft.txt.
Sections
The course’s nine (core identity, registers, sentence patterns, rhetorical moves, emotional register, do’s and don’ts, quick reference, calibration tests, AI tics to avoid) plus three of mine: how to use the guide, cover letters and resume summaries, and growing the guide from my edits.
Inputs
My notes, rough draft or facts, and the kind of message.
Outputs
A draft in the right register, and a checker report with FAIL and WARN lines (em dashes, banned phrases, overused words, no closing question).
Feedback loop
After I send a resume or letter, the .docx I sent is compared with Claude’s markdown draft, and each sentence I changed is saved as a before-and-after pair.
Build your own
Collect writing from before you used AI and run the course’s nine-section prompt on it instead of your recent sent email. Then have two drafts written with the guide and two without, and rate them blind.

Known limit: the corpus holds one pre-AI work email and no cover letter I wrote myself, so the email and cover-letter rules are a starting set, corrected from my edits. And my own words still beat the guide. When Claude has my notes, it should use them.

Build 04Shipped

Email Manager Scheduled Task

A daily system that labels, sweeps, and summarizes my Gmail: rules run as code, and Claude handles only what the rules can’t.

New to me: scheduled AI tasks

01 · The problem

An inbox I never check still fills up.

Outlook is my main email, and I spent weeks cleaning it up with sweep rules, folders, and unsubscribes. My Gmail got none of that. When I connected Claude to it, the inbox held 1,144 threads, 885 of them unread. A few account and billing notices that needed me were buried under job alerts, store promotions, and newsletters.

02 · The approach

Plan first, then act.

I didn’t let Claude change anything at first. It read the whole inbox and wrote a plan: every recurring sender, what it is, and a proposed action. I marked up the plan with my decisions, and only then did it build.

The result is 14 labels. Eight are kept for good (finance, receipts, security, people, employers, AI services, AI news, lawsuit notices). Six are swept: anything in them is trashed after 10 days, or after 3 for marketing I’ve unsubscribed from.

03 · Key decisions

Code for the rules, Claude for the judgment.

Labeling a known sender or trashing a 10-day-old job alert never needs judgment, so a Google Apps Script does it: 49 sender rules become Gmail filters, and a daily sweep trashes by label and age. It runs free, every day, with my computer off.

A scheduled Claude routine runs each morning in the cloud. It finds senders no rule covers and proposes new rules I can paste in, reads the job-scan emails, flags anything that needs me, and lists my meetings for today and the week. It never deletes or sends. It leaves one draft for me to read.

04 · What went wrong

The job reports had no jobs in them.

A daily AI job scan had sent 251 reports. When Claude read one, it held a three-line summary and a link; the roles themselves were on another site. The top match that day was a company that had already turned me down a month earlier, so the scan didn’t know my history either.

Two smaller ones: the Gmail connector can’t see the spam folder, so the script reports on spam instead; and Claude’s first delete was blocked until I granted that permission myself.

The spam report turned up 156 threads. 155 were scams, each from a throwaway domain, so blocking senders would do nothing. One was a real class-action settlement notice I could claim. Claude had also flagged an older settlement email in my inbox as phishing; it was real too. Now both go to their own label.

05 · What I’d change

Make the scan send the jobs themselves.

Next I’ll change the job-scan prompt so each email lists the roles, and have the morning routine check them against my application tracker. Then I’ll run the same setup on my other Gmail accounts.

Keeps a Gmail inbox near zero: known senders are labeled on arrival, swept labels are emptied by age, and a morning summary covers what the rules missed.

Deterministic part
A Google Apps Script with two tables: labels with a keep-or-sweep period, and sender rules. One-time functions create the labels and filters, label existing mail, move old receipts, and unsubscribe through each sender’s one-click link. A daily trigger runs the sweep. Starred mail is never touched.
Claude part
A scheduled Claude Code routine (cloud, daily at 7am) with the Gmail and Google Calendar connectors. It reads the script’s rules from my workspace so it knows what’s already handled.
Outputs
One draft each morning: what needs me, proposed new sender rules, job-scan roles, today’s meetings, and this week’s.
Guardrails
The routine is read-only except for that draft. Email text is treated as data, never as instructions. Deletes go to Trash, which keeps them 30 days.
Results on day one
The first sweep trashed 894 threads in four minutes: 438 job scans, 255 hobby newsletters, 182 from marketing I’d unsubscribed from, and 19 more. 13 of 19 marketing senders unsubscribed by one-click link; 6 need a manual opt-out. The first morning draft found no sender the rules missed.

Known limit: Gmail filters act only when mail arrives, so age-based rules need the script. Unsubscribes without a one-click link still need a person.

Build 05Shipped

Spreadsheet Analysis

My job-search data turned into answers: SQL views, a formula-driven Excel workbook, and charts that redraw after every pipeline run.

Builds on: Sheets Decomposer, AdoptiScope, Requirements Fit Analyzer, and Forester

See the charts ↑

01 · The problem

Thousands of graded roles, and no way to see the pattern.

My Requirements Fit Analyzer scores thousands of job postings against my record. The answers I needed were in there: which industries fit me, which lens drives the fit, and which good fits I had never applied to. But the data sat in a database the pipeline locks for hours at a time, and nothing rolled it up.

02 · The approach

Ask the question first, then pick the chart.

I told Claude what I wanted to learn, not which chart to draw. It proposed the measures and the forms: a bar chart for fit by industry, a scatter for posting volume against fit, a heatmap for industry by lens, and a stacked bar for the grade mix. I picked the ones that answered my question and cut the rest.

Then I split the work by audience. A public version shows industries and percentages only. A private Excel workbook shows each employer and drives my next applications.

03 · Key decisions

The database does the math, and formulas keep the workbook checkable.

Everything queries a PostgreSQL copy of the pipeline’s results, never the working database, so a report never waits on a run. SQL views hold every calculation once. Excel and the charts use the same views, so they always agree.

The workbook’s summary tabs are formulas over a data tab, not typed numbers. A filter or a fix in the data recalculates every total. The charts are drawn by a short script in the site’s colors, and the pipeline starts it 45 seconds after each snapshot finishes.

04 · What went wrong

The first answer was too good to be true.

The first count said I had never applied to most of my good fits. Some of those I had applied to. Older tracker rows were missing the posting ID that links an application to a posting, so applied roles looked untouched. The fix is in the data, not the chart.

The second surprise held up. Fit on paper is not the same as interest from employers. Most of my screens so far came from the industry where I fit worst on paper. The workbook now tracks responses next to fit, so I can see both.

05 · What I’d change

Keep history, and close the gaps in the old records.

Each run replaces the snapshot, so I can’t chart change over time yet. Next I’ll keep a small daily history table for trend lines. I’ll also map the company names in my older application records, so response rates cover every application, not just the newer ones.

Rolls my job-search pipeline’s graded postings and application history into views, a workbook, and charts, and refreshes them all after every run.

Inputs
The pipeline’s nightly PostgreSQL snapshot of active postings and grades, my application tracker, and a map from employer to industry.
Deterministic part
Nine SQL views compute fit by industry, employer, and lens, the workplace mix, the untapped good fits, and the application funnel. A standard-library Python script draws five SVG charts. A second script writes the Excel workbook with native charts.
Outputs
Five public charts (industries and percentages only) and a private workbook with seven tabs: Industry, Employer, Lens, Untapped, Applications, Data, and a README.
Trigger
The pipeline’s launcher starts the refresh 45 seconds after each snapshot. It skips the work when nothing changed, and a chart file is rewritten only when its numbers change.
Checks
I had Excel itself open the workbook and recalculate it: about 49,900 formulas, no errors, and totals that match the database. Every chart was rendered and checked by eye before it went on the page.
Sheets Decomposer
Turns a large inherited workbook into living documentation.
AdoptiScope
Generates an Excel workbook, a Google Sheets version, and a docs site in sync.
Requirements Fit Analyzer
Supplies the graded data, and refreshes a Google Sheet copy of my tracker.
Forester
Imports and exports Excel models and BI insights.

Known limit: fit rates are shares of the shortlist the AI judge graded, not of every posting. Every chart says so in a footnote.

Build 06Shipped

Data Analysis Presentation

Six slides from my job-search data, designed in Claude Design and rebuilt after every pipeline run.

Builds on: Requirements Fit Analyzer and the data migration assessment

Presentation

01 · The problem

A typed deck would be out of date after the next run.

The course asked for a data presentation: six slides or fewer, one point per slide, and a title on each slide that states the finding. I already had the dataset. My Requirements Fit Analyzer grades thousands of open roles against my record every night, so any number I typed into slides would be wrong by the next morning.

02 · The approach

Design it once in Claude Design, then let the data fill it in.

I gave Claude Design my site’s style guide (the colors, fonts, and spacing pulled from this site’s stylesheet) and a six-slide outline I had approved, and asked for a deck that looks like this site. The first draft matched well enough that I kept it as the design.

Then Claude Code rebuilt that design as a Python script. The script reads the same PostgreSQL views as my Build 05 charts, fills in every number, and writes the deck as one HTML file you can page through with the arrow keys. Press N for my speaker notes.

03 · Key decisions

Every headline is a claim the script checks first.

A slide title like “Healthcare and consulting fit me best” has to stay true after the next run. The script tests each headline against the data before it writes it. If a pattern changes, the slide switches to a neutral title instead of printing something false.

The same refresh feeds two audiences. The public deck shows industries and percentages only, and a small workbook lists each figure next to the view it came from. A private report goes one level deeper, to each employer: which ones have good-fit roles I haven’t applied to, which ones answered me before, and which ones haven’t answered after several applications. I keep it open next to my tracker spreadsheet when I decide which job descriptions to read next.

04 · What went wrong

My own outline had a false headline.

The approved outline said “Most of my good fits are remote.” Checking the numbers before the build showed remote leads at 44.5%, which is not most. The slide now says remote leads, and the script picks that headline from the data on every run.

The private report hit a matching problem. My tracker and the job boards spell the same company differently (“Booz Allen” and “Booz Allen Hamilton”), and only about a third matched exactly. The report now normalizes company names before it joins them.

05 · What I’d change

Count every response, and keep history.

About half my older applications came over from a spreadsheet without their status history, so the report undercounts screens. I’d backfill that history first. I’d also keep a daily history table so the deck can show change over time, not just today.

Turns my job-search pipeline’s nightly results into a six-slide presentation and a private focus report, rebuilt after every run.

Inputs
The pipeline’s PostgreSQL snapshot of graded postings, my application tracker and its status history, and the employer-to-industry map from Build 05.
Design
A Claude Design draft, prompted with my site’s style guide and the approved outline, then rebuilt in code so it matches the site.
Deterministic part
A Python script computes every figure from SQL views, tests each headline against the data, and writes the deck as one self-contained HTML file: fonts inside, no network calls. A second script writes the private report the same way.
Outputs
The deck with speaker notes, a workbook (my-data.xlsx) with each figure and its source view, and a private employer-level report with filters, sorting, and a link to each posting.
Trigger
The same refresh that redraws the Build 05 charts, 45 seconds after each pipeline snapshot. Refreshing the browser shows the new version.
Checks
Every slide was rendered and checked against the approved design. The speaker notes passed my voice checker. Each headline has a fallback for when its pattern flips, and the deck’s numbers match the charts because both read the same views.
Requirements Fit Analyzer
Supplies the graded data and the questions the deck answers.
Data migration assessment
The same move from raw data to a go/no-go decision, told to decision makers.

Known limit: fit rates are shares of the shortlist the AI judge graded, not of every posting. Every data slide says so.

File Organization Process

A folder system my AI tools can find their way through: four top folders, one spec, and scripts that check it.

Builds on: Keystone’s folder structure

01 · The problem

Years of files, and an AI that had to search for everything.

Keystone keeps my work, my faith projects, and the skills my AI tools use: about 158,000 words in the skill files alone. When files lived wherever I saved them, every session started with a search, and the AI filled the gaps with guesses.

02 · The approach

One spec decides where every file goes.

I wrote the rules down once, in a spec the AI reads before it creates, moves, or deletes a file. Professional and Personal are PARA trees: Projects have an end date, Areas are ongoing, Resources are reference, and Archive is anything inactive. System has the AI’s working files: personas, skills, lessons learned, and the index.

System/
The AI’s working files: Context/Personas, Context/Skills, Context/Learned, Context/Indices, plus the Backlog
Professional/
Projects, Areas, Resources, Archive for work
Personal/
Projects, Areas, Resources, Archive for life and faith work
Root
CLAUDE.md, two pointer files, and the README. Nothing else.

03 · Key decisions

Every file has one home, and the index points to it.

Three principles keep it that way. One topic per file, and edit an existing file before creating a new one. Every new file gets a line in the index in the same change, or it will never be found. Nothing lives in the root except the instruction file, its two pointers, and the README.

04 · What went wrong

My AI’s memory became a second, messier vault.

Claude keeps its own memory notes, and by October they had grown past a hundred files, many repeating facts already in the vault. On October 2 and again on October 19 I moved every lasting fact into the vault and cut the memory index down to pointers.

05 · What I’d change

Schedule the audit instead of remembering it.

The index check and the skill audit are scripts I still run by hand. I’d put a weekly folder audit on a schedule, the way my Email Manager runs.

A written spec and two audit scripts that keep a large vault organized for both me and my AI tools.

Before
Files saved wherever I was working, instructions copied per tool, and facts kept in the AI’s memory notes.
After
Four top folders, PARA inside Professional and Personal, one spec, and one index line for every skill, persona, and lesson file.
Rules
Read the spec before creating, moving, or deleting a file. Ask me before deleting or restructuring. File names avoid special characters so the vault opens on my iPad.
Sync
A job on each machine pulls, commits, and pushes every 10 minutes. AI tools commit only the paths they changed.
Checks
skill_audit.py checks every skill file against the authoring standard, and a one-line shell check lists any file the index never mentions.

Audit prompt: “Audit this folder against its spec. List files with no index line, files in the wrong PARA folder, duplicate topics, and bad file names, as a table. Don’t move anything. Wait for my decision.”

Build 08Shipped

AI Context File

One file that lets every AI session start out knowing who I am and how I work.

Builds on: Keystone’s single instruction file

01 · The problem

Every tool started from zero.

I use Claude Code, the Claude app, Gemini, and Copilot. Each one needed to know who I am, how I want answers, and which rules never bend, and I was repeating it.

02 · The approach

One instruction file, read first by every tool.

CLAUDE.md is in the vault root and runs about 230 words. Gemini reads agent.md and Copilot reads COPILOT.md, and each of those is two lines: a sentence that says to follow CLAUDE.md, and an @CLAUDE.md line that pulls the full file in. Claude, Gemini, and Copilot all start from the same instructions, open the same index, and work in Keystone the same way. It covers what to do every session (read the backlog, find the task in the index, log what’s left open at the end), the rules, and how I want answers: lead with the answer, use tables, flag concerns briefly, push back when asked.

Every session
Open the backlog, find the task in the index, load only the pages it needs, then log what’s left open and commit.
Rules
Read the spec before moving files, ask before deleting, commit only my own paths, never put secrets in the vault.
Every agent
agent.md (Gemini) and COPILOT.md (Copilot) import CLAUDE.md with an @CLAUDE.md line, so every tool follows one set of instructions and I edit one file.
How to answer
Lead with the answer, use tables, flag concerns briefly, push back when asked to red-team.

03 · Key decisions

Keep the file small and let it point.

The context file doesn’t hold my full story. It points to the index, the index points to one router per domain, and the router points to the few pages a task needs. A typical task reads about 3% of the documented skills. Facts about me live in persona files, like my voice guides, so they load only when the writing calls for them.

This is a little more flexible than setting everything up inside the Claude app. Custom instructions there only reach Claude. My files are markdown in a git repo. Any agent that can read a file can use them, the Claude app included: Cowork opens the Keystone folder, reads the same instructions and skills, and reaches my scripts through local MCP servers. The vault lives on my Windows drive, so Claude Code in WSL and the Claude app on Windows open the same files. Git versions every change and replicates the whole vault to a second computer running Linux, where it works almost exactly the same: the same agents read the same files, with the same Python environments and a PostgreSQL copy of my main database that is never more than an hour behind. One design covers WSL, Windows, Linux, and every agent I use.

04 · What went wrong

Two copies of the same instructions drifted apart.

Gemini had its own copy of the instructions. On September 9 I had to sync it back to Claude’s by hand. On October 19 I made CLAUDE.md the single source and turned the other files into pointers, so they can’t drift again.

05 · What I’d change

Generate the app’s settings from the same source.

The Claude app has its own custom instructions and memory settings, outside the vault. I’d generate them from CLAUDE.md so there is still one source.

Builds on: Keystone’s skill routers

01 · The problem

The same instructions, pasted again every week.

Resume bullets, Bible study steps, lesson production, job-search runs: I kept explaining the same procedures, and each explanation came out a little different.

02 · The approach

A router per domain, with reference pages under it.

Each family has one router that sets the order of work and sends each kind of request to one reference page. Claude Code reaches them through thin skills of about 12 lines: a trigger description and the router’s path. The course skills joined the same library: my design system, my write-up skill, my voice guides, and the Email Manager. Skills saved only to my claude.ai account work only in Claude. Skills kept as files in Keystone work in Claude Code, the Claude app’s Cowork, Gemini, and Copilot.

03 · Key decisions

Load only what the task needs.

I chose routers because the alternative was loading every procedure into every session. Until a request matches, a thin skill costs Claude only its trigger description and a path. The router then sets the order of work and sends the request to one reference page, so the detail arrives only when the task calls for it.

This follows Anthropic’s guidance on context engineering, which I used as source material when I refreshed my Keystone context files: give the model the smallest set of high-signal information that does the job, and load the detail just in time instead of up front.

04 · What went wrong

One giant skill was too big to load.

The job-search instructions grew into one long file. On October 2 I split it into a router and 23 reference files, wrote a wide-and-shallow standard for every skill family, and added skill_audit.py to flag any file that breaks it.

05 · What I’d change

Run the audit on a schedule.

I’d run skill_audit.py monthly as a scheduled task, and again whenever a new Claude model ships.

How I’ve used AI

What changed across four sessions.

I built nine things in four sessions: a design system skill, a portfolio site, a voice guide, a scheduled email manager, a spreadsheet analysis, a data presentation, a folder system, an AI context file, and a skills library.

Three things changed in how I work with AI. I stopped retyping context: CLAUDE.md loads first in every tool. I check AI’s writing with code: voice_check.py tests every draft against Voice_Guide_Professional.md before I read it. And I let the pipeline do the reporting: refresh_reporting.py rebuilds my charts, my deck, and a private focus report after every snapshot.

My strongest build is the data presentation. One refresh now produces six slides with speaker notes, a workbook that traces every figure to its source, and an employer-level report I keep open next to my tracker when I decide which job descriptions to read. It also caught a false headline in my own outline before it went public.
