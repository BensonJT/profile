Agents: The Agent Calls the Code

Give the Agent Engineered Context and a Curated Toolbox

Jeffrey Benson  ·  2026

Deterministic First: Agentic Systems  ·  Part 1  |  Part 2  |  Part 3

In one of my Bible study lessons, the AI narrator read "to Timothy" twice. In another, it got caught in a loop on "to the praise of His glory" and repeated about 330 words, turning out 518 seconds of audio for 1,196 words of script. Both requests came back as finished audio files, with no error.

I didn't find either one by listening to everything. A script transcribed each audio file back into text and compared it word for word with the narration script, and I listened closely only at the places it marked. We divide the work this way: when the comparison shows a clear error (a doubled phrase, a looped passage, a dropped line), the agent requests a new take of that piece on its own. Only the cases the comparison can't settle, such as a possible mispronunciation or a misread name, come to me.

For one lesson (101_005 in my Abide course), the agent produced 20 audio files: ten sections, each in two voices. The comparison matched between 96.1% and 100% of the words in every file, and it gave me a short list of specific spots to check by ear. My own listening then caught two things the comparison could not: a word said wrong ("exegetical") and a scholar's name said badly. The agent retook both pieces.

This article will not teach how to build an agent from scratch. Rather, we will look at how an agent that owns its own path can still be deterministic first: what it is given to read, which tools it is handed, and where a script checks its work. Part 1 covered workflows, where code owns the path. Here the model owns the path and calls the code.

Why an agent

The path lives in written instructions

In Part 1, a workflow's steps were written in code. In Abide production, the steps are written in skills: instruction files in everyday language that Claude Code (Anthropic's coding agent, as of November 12, 2026) reads and follows. The agent decides which step comes next.

Anthropic's guide recommends an agent when it is "difficult or impossible to predict the required number of steps," and when there is "some level of trust in its decision-making" (Schluntz and Zhang 2024). Lesson production fits that description. One night a voice service refuses a Scripture passage, the next night a request hangs, and a name keeps coming out wrong across three takes. Nobody could write those branches in advance.

The same guide calls the building block of every agent the augmented LLM: "an LLM enhanced with augmentations such as retrieval, tools, and memory." In my setup, the skills are its instructions and memory, and the tools are below.

The toolbox

54 purpose-built scripts, a few at a time

As of November 12, Abide production has 54 purpose-built scripts, 7 of them tests. Thirty-six live in the course's working folder, 8 in the website's code, and 10 are Scripture tools shared with my FaithOnline writing. Grouped by job:

Under these is a much larger standard toolset the agent already knows how to use: the Linux command line, Python environments for the scripts, faster-whisper for transcription (SYSTRAN), ffmpeg for audio and video (FFmpeg), git and a cloud storage command line. The voices come from Gemini's text-to-speech models (Google, as of November 12, 2026).

Browser control extends the toolbox. With Claude in Chrome (Anthropic), the agent also produces each lesson's Gemini Notebook study guide and explainer video. Those two come last, after I sign off on their inputs (the article, the teacher's session guide and the slides), so the agent builds them from approved material only.

A curated toolbox. Anthropic warns that "one of the most common failure modes we see is bloated tool sets that cover too much functionality or lead to ambiguous decision points about which tool to use," and adds, "If a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better" (Rajasekaran et al. 2025). Fifty-four scripts can sound like the bloated set it warns about. Each one has a single job, though, and each skill step lists only the few scripts it needs. The agent loads a step's instructions when it reaches that step, which Anthropic calls progressive disclosure: skills "let Claude load information only as needed" (Zhang, Lazuka and Murag 2025). The agent sees a handful of tools at a time.

Tools spend less than tokens. The Agent Skills article puts it in one example: "sorting a list via token generation is far more expensive than simply running a sorting algorithm. Beyond efficiency concerns, many applications require the deterministic reliability that only code can provide." The agent spends its tokens on judgment. The tools give the same answer every time, at almost no cost.

Ground truth

What the agent checks itself against

Anthropic's guide says "it's crucial for the agents to gain 'ground truth' from the environment at each step." In Abide, the ground truth has three parts, and none of it is a model's opinion:

  • The scripts' results: a match percentage, a count of missing quotations, a pass or fail.
  • The research files. Every passage I copy from a commentary in Logos Bible Software is moved into the lesson's research file byte for byte, and check_pastes.py confirms it is still unchanged.
  • Scripture pulled by script or API, in its own translation, never typed from memory. bsb.py reads a local copy of the Berean Standard Bible, which is in the public domain (Berean Bible). lockman.py fetches the LSB, NASB and AMP from The Lockman Foundation's site (Lockman). msb.py, esv.py and API.Bible (API.Bible) cover the rest.

Deterministic evaluators

A script in the evaluator's seat

Anthropic describes an evaluator-optimizer pattern, in which "one LLM call generates a response while another provides evaluation and feedback in a loop." Abide puts a script in the evaluator's seat wherever there is one right answer. Here is the audio check in five steps.

1. The question it answers. Does this audio file say what the script says, word for word?

2. What goes in. The audio file and the narration script it was made from.

3. What it does. A speech-to-text model transcribes the audio. The script lines the transcript up against the narration script and lists every word skipped, added or changed. Names are written in the script as pronunciation spellings (for example, /spuˈdɑzoʊ/ for a Greek word), so the comparison treats them as wildcards and every name gets a targeted second listen. Let's work one. The script says "written to Timothy in Ephesus." The transcript says "written to Timothy to Timothy in Ephesus." The comparison lists two added words at that spot.

4. How to read it. The result is a match percentage for the file and a list of places to listen. Most files I approved scored 98% to 100%. A file below 97% gets a closer look. One short section fell below that line mostly because it contains one scholar's name three times. Added words in a row, like the example, are a clear error, and the agent retakes that piece itself. A single changed word is often the transcriber mishearing, so it goes on my list.

5. Where it is used. On every audio file before I hear it. A second pass with a larger transcription model then clears most of the listed spots as mishearing. For lesson 101_005, five spots were heard the same wrong way by both transcribers, and I listened to those first.

My attention moves from "listen to everything for anything" to "decide on the places a machine says differ," followed by one full listen while I follow along in the text.

Where the evaluator still needs a person. When a file scores between 98% and 100%, I still listen at each spot the check lists, to confirm which ones are real defects. The transcript comes from a model too, and a model can mishear. The defect may be in the transcript, while the audio file we are checking is fine. Of the five spots both transcribers heard the same wrong way in lesson 101_005, three sounded right when I listened ("in words," "about his sin" and "John writes"), so the audio was correct and both transcripts were wrong. One was a real defect: "led the way back" came out "led the will back," and the agent retook it. The script tells me where to look, and I decide whether the defect is in the audio or in the transcript.

Quotations get the same treatment. For lesson 101_006, check_quotes.py confirmed 443 quotations across the lesson, the slides, the handout, the teacher's packet and the study guide, with none missing from their sources. check_paraphrases.py confirmed that each of 87 paraphrases rests on words a source wrote. check_lesson.py ran 19 checks, all passing. For Scripture in particular, lockman.py --check and bsb.py compare each quotation with its translation's text and exit with an error on any difference.

Of everything in this series, this is the pattern I'd most like other teams to try: a deterministic evaluator inside an agent's loop, with human review moved to the places the evaluator flags.

Error-proofing

Tools that refuse bad input

Anthropic's own advice on tools borrows a term from manufacturing: "Poka-yoke your tools. Change the arguments so that it is harder to make mistakes" (Schluntz and Zhang 2024). Poka-yoke is the Japanese term for error-proofing. Abide's tools refuse bad input:

  • narrate.py refuses a section that still has a [CHECK] marker, so nothing uncertain is ever voiced.
  • move_paste.py refuses a research paste whose source citation is above it, so every citation stays right below the words it credits.
  • A step doesn't count as done until check_lesson.py reports zero failures.

The agent owns the path, but some gates are enforced by code it can't talk its way past.

Qualifying the checkers

Who checks the checker?

A checker is an appraiser too. The five test files for the audio, narration, quotation, paraphrase and paste checkers hold 66 tests, and many come in pairs. A quotation with the right verse must pass, and the same quotation with the wrong verse must fail. The same goes for the right and wrong author. That is the Measurement Series applied to the evaluators themselves (Part 4): before a checker is trusted, show that it catches what it should and passes what it should.

Choosing

When a workflow, when an agent

Here is the rule I use today. Treat it as a draft.

In practice the two mix. An agent (Claude Code) built both workflows in Part 1. In both patterns, the most expensive layer is used last and least.

Glossary

Terms used in this article

Agent
An agentic system in which the model decides its own next step and which tools to use.
Augmented LLM
A language model given retrieval, tools and memory. Anthropic calls it the building block for agents.
Skill
A folder of written instructions, and often scripts, that an agent loads when a task calls for it.
Progressive disclosure
Loading a skill's detail only when the agent reaches the step that needs it.
Context engineering
Choosing and maintaining what the model has in front of it at each step.
Ground truth
A result from the environment the agent can check against, such as a script's output or a source text.
Evaluator-optimizer
A loop in which one step produces work and another evaluates it and sends feedback.
Deterministic evaluator
A script in the evaluator's seat: it gives the same verdict every time for the same input.
Text-to-speech (TTS)
A model that turns written text into spoken audio.
Transcription
Turning speech back into text with a speech-to-text model.
Poka-yoke
Error-proofing: designing a step so that a mistake is hard or impossible to make.
MCP server
A program that offers tools to an AI agent through the Model Context Protocol.
