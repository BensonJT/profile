Product · Private MVP

Forester

My process-modeling method, turned into software. Capture a process once, as data, and Forester draws six standard diagrams from it at every level of the decomposition, computes the full Lean Six Sigma metric stack, and coaches the modeler on the method as they go. 1,375 commits and 18 sprints, much of it built by an autonomous AI loop working from specs I wrote and reviewed. Not publicly launched.

Evaluated: a blind test settled how Claude reads fraction fields; two implementations must agree on about 890 cases.

01 · The problem

The method only scaled as far as I could.

For thirty years my process work ran on one method: decompose the work, then at every step capture who supplies and receives what, the inputs, controls, outputs, and mechanisms, and the time and value in each step. It works, but only when I run the interviews and draw every diagram by hand, one diagram at a time.

02 · The approach

Capture the model once and compute every diagram from it.

Forester is a web app: a React and TypeScript workspace, a FastAPI backend, and Postgres. You build the process as a tree, edit it as a tree, a spreadsheet, or one step at a time, and every diagram and metric is computed from that single model: flow efficiency, rolled throughput yield, sigma level, Cp and Cpk, required staffing, equipment effectiveness, and the cost of poor quality. It imports and exports JSON, CSV, Excel, and BPMN files, behind a preview that writes nothing until you confirm.

The build ran on binding sprint plans. Claude Fable reviewed each spec for any place the builder would have to guess; one pass found 5 blockers and 8 unstated judgment calls, each settled with my ruling before work began. An autonomous loop running Claude headless then took one task at a time with a fresh context, ran its tests, and committed: 313 commits came from that loop. Judgment-heavy stages I built interactively with Claude Opus. 1,375 commits from May 18 to September 26, 2026, and 31 architecture decision records.

03 · Key decisions

Store each arrow once.

One data model. Each input, control, output, or mechanism arrow is stored once, and is at the same time an edge in every diagram and an input to the metric roll-ups. Diagrams are views of the model, never separate drawings to keep in sync.

Every metric written twice and checked. Each formula exists in TypeScript for the screen and Python for the server, locked to shared test fixtures so the two can’t drift, and governed by one canonical metric catalog.

One owner for every fact. Each kind of fact, from the database schema to the roadmap, has exactly one document that owns it, and a change to the code updates its owner in the same commit. The metric catalog stayed clean for eleven sprints under that rule, so I made it the rule for everything.

04 · What went wrong

Real client work found what demo models didn’t.

The first paying engagement modeled in Forester exposed that the order of steps in the BPMN export was inferred from the tree rather than declared. That cost an unplanned sprint: flow became explicit data, and round-tripping the real model took five rounds of fixes before it came back intact.

The loop has failure modes too. One stage was built from the sprint plan instead of the design and had to be rebuilt by hand, which is why specs now get that critical pass before the loop runs.

05 · What I’d change

The interview is still ahead.

The feature that matters most, an AI interviewer that runs the conversation I used to run by hand and captures the model as it goes, isn’t built yet. Neither are accounts for multiple customers or the executive dashboards. The foundation came first on purpose; the next phases build on it.

A process-modeling workspace that turns one captured model into six diagram types and a full Lean Six Sigma metric stack. Phase 1 is a private, single-user product that is feature-complete and being hardened; it is not publicly available.

Meridian

An AI-assisted research system for a private investor, in daily use since August 2026. I modeled the client’s operating process first, in Forester, and its five operating modes became the architecture’s top level. Every number is computed by deterministic code; AI reads language where language is the task. 1,693 commits and 4,310 automated tests. Client-confidential: no code, screens, or data sources shown.

Evaluated: four models on 120 frozen articles, against bars written before any run.

How I evaluate it → What it does for a client →

Meridian runs on two clocks: a news lane three times a day, and an overnight batch I schedule. Every step is safe to rerun, so a missed or skipped slot loses nothing.

Scheduled: news lane
Three times a day. It pulls news and options data for every active ticker, scores the new articles with a language model (newest first), and derives events against the market calendar. It checks the data vendor’s remaining credits first; when the free tier runs low, it skips the pull but still scores the backlog.
On my schedule: overnight batch
I pick a start time and the laptop wakes itself to run the batch, which finishes before the market opens. It pre-flights twice: once when I confirm, so a problem shows up before I go to bed, and again at the start time.
Triggered
Checks that fire from a calendar of known releases, and a file import that routes each file by type or stops with an error.
Guardrails
Locks keep the news lane from colliding with the batch: if the batch is running, the news slot stands down and the next one catches up.

Why not daily: the batch would run every night if my hardware allowed it. On the client’s machine it does.

01 · The problem

The research lived in many places, each read by hand.

The investor’s research ran across separate data services, spreadsheets, and broker exports, each opened and read by hand. They needed one place to read the morning’s picture, with the numbers computed once and reconciled, while their own thinking stayed on their own machine.

02 · The approach

Model the process first, then build the system around it.

Before any code, I modeled the client’s operating process in Forester. Its five top-level activities, from the overnight batch to the investor’s own routine, became the architecture’s top-level decomposition word for word, and every component exists to serve one of them. Putting the investor’s own routine inside the boundary is why the file inputs, the dashboard, and the setup agent were designed in rather than bolted on.

Underneath sit seven layers: scheduling, one ingest harness per source, PostgreSQL with append-only history, deterministic analytics, language-model work, report generation, and a local dashboard with 12 views. The sources were chosen from more than 20 evaluated in a written scoring before any was adopted.

1,693 commits from July 8 to October 20, 2026: 500 from an autonomous loop working headless from written specs, and 127 from the client’s machine, where a coding agent applies each migration and reports diagnostics back, because I never have a shell there.

03 · Key decisions

AI explains the numbers but never computes them.

A never-AI zone. Price math, technical analysis, money flow, and reconciliation are deterministic code only. When numbers enter a prompt they arrive pre-computed, so a model can narrate vetted numbers but can’t introduce an arithmetic error. Language models are used where reading language is the task, starting with scoring the news.

Free hosted models, chosen by test. The news is read by Gemma 4, an open-weight model, on Google AI Studio’s free tier. A local model on the investor’s own machine was the first plan, but neither machine is big enough for a local model that does the job well; the small local model in the bake-off scored 28%. The tradeoff is volume: the free tier limits how many articles get scored each day. If a model fails, the system falls back to another free model, never silently to a paid one, and failure alerts use fixed text so they still fire when the AI stack is down.

Fetch and compute are separate. Ingest scripts only fetch; every calculation pulls the stored data in its own script, and everything derived recomputes whenever the data underneath it moves. That rule was locked after an early script computed from a redundant API pull and disagreed with the local data on most rows.

04 · What went wrong

The quiet failures were the dangerous ones.

On the client’s machine, blocked network calls degraded runs without stopping them, so for a stretch no overnight run finished and nobody heard about it. That produced egress checks, a diagnostic report the client’s agent pastes back, and a rule: a failure that isn’t fatal must still raise an alert. A database outage also left no record of itself, because the run log lived in the database; an append-only local log now records lost runs and replays them when the database returns.

A full-pipeline audit turned up 249 open findings and became a ten-stage remediation sprint, and the plan for the next sprint was scrapped and rebuilt around it. The first production run also crashed on the client’s Mac, whose built-in shell dates from 2007, so every script was reworked to run on both systems.

05 · What I’d change

Make every failure visible before the first overnight run.

The alert rules came after the silent stretch. Starting again, they would exist before the system ran unattended for the first time. Next on the list: finishing two historical data loads on the client’s machine and speeding up the overnight run.

Requirements Fit Analyzer

A system that reads requirement documents and measures how well each one fits a verified evidence record. Its first job is my own career search: it reads postings straight from employers’ own hiring systems, keeps a true history of each one, and ranks the open ones against my record. Cheap, deterministic steps do the volume work; AI models only judge a small, gated shortlist, and only after passing the same kind of measurement-system study I’d run on any gauge. Every decision is still mine.

Evaluated: every model measured like a gauge against my blind fit grades, keeping only the role it passed.

Fit rates are shares of the shortlist the AI judge graded, not of every posting. Cheap screens narrow the pipeline first, and only that shortlist is graded.

01 · The problem

The job boards were showing me jobs that had already closed.

My first attempt, in March 2026, pulled from job aggregator APIs. The matches were mostly postings that had closed weeks earlier, and on one run every aggregator link I followed returned an error. The employer’s own hiring system is the only source that is always current.

Collection was only half of it. Tens of thousands of live postings is too many to read, and keyword search can’t tell a role that matches the work from one that only shares its vocabulary.

02 · The approach

Read the source, then narrow it in stages.

On September 15, 2026 I started over. The new pipeline pulls the same data each employer’s careers page uses, across 13 hiring-system platforms, into a single DuckDB file. A full sweep covers 180 employer boards and about 86,000 postings in 16 minutes. Nothing is ever deleted; a posting is closed only when a clean, complete pull no longer lists it.

Then a funnel. A rule engine screens on title, location, pay, clearance and level. Trained models score fit on three lenses: process, technical and applied AI. Embeddings match each requirement line to my record and name the one most likely to be unmet. At the end, TypeSafe AI’s Jev, a model built for fast typed decisions, reviews the shortlist and can demote a row. The result is one page: every score visible, one rank, one reason. I read it and decide.

The build used AI the same way. Claude Fable designed and audited, Claude Opus built from a binding spec, and for the Jev work, Opus builder agents each built one work package in its own git branch, audited and merged before the next one depended on it. 301 commits in 36 days.

03 · Key decisions

Treat every AI model like a gauge that has to earn trust.

Deterministic first, AI last. The free steps do the volume work. Paid model calls touch only a small gated subset, under token caps, and every live call needs explicit approval after a dry run that shows the exact request.

Distill, don’t prompt-tune. I had 362 good matches and only 7 audited near misses, and nothing can be tuned reliably against 7 examples. Instead, Claude Sonnet graded 3,634 postings, and those grades trained small models that score the whole corpus for free, at AUCs of 0.92, 0.89 and 0.93. Sonnet won the grader job by measurement: on the same 25 postings, Opus graded systematically more generously.

An AI judge is an appraiser. Before Jev could demote anything, it went through a measurement-system study against my blind grades: it caught 91% of what I caught, agreed 93% of the time, and flipped an answer on a repeat question 1.6% of the time against a 2% bar. It’s also tested for prompt injection and pinned to one model version. My calls outrank every model, and a grade only counts toward evaluation if I gave it before seeing any machine score.

04 · What went wrong

Some of the smartest-looking parts failed their own tests.

Matching requirements with embeddings looked like the obvious ranker. It wasn’t: similarity scores bunched so tightly that it reached an AUC of 0.669 against the fit model’s 0.955. It now explains a ranking instead of making one.

A Gemma second judge failed its accuracy bar eight rounds running and was retired from the nightly run; it now only appears as evidence beside Jev’s demotions. And for ten days in October the demotion pass was silently off while the page said it was active, because edits created prompt versions that had never been measured. The gate now re-measures itself, and the page warns when it can’t.

05 · What I’d change

Close the loop on every disagreement.

Next is turning each place Jev and I disagree into a recorded ruling, then re-measuring Jev against them. A newer Jev version gets the same gold-score test before the pipeline moves off the pinned one. And nine tests that seed a fixed date need fixing: they have failed since October 1 because the date aged out.

Work sample

Data migration assessment

A public take-home for a government data engineering role, run as a quality problem rather than a row-count check: sigma levels and yield field by field, rolled into a go/no-go scorecard. Runs end to end on CMS public data.

What it does for a client →

01 · The problem

A row count says the migration worked.

The exercise: compare a legacy claims system’s output with a new system’s before cutting over, find the discrepancies, and size their impact. Matching row counts would have passed a migration that was missing thousands of claims.

02 · The approach

A pipeline that treats every field as a quality opportunity.

I built it with Claude Code from February 9 to 12, 2026: Python and DuckDB, ingesting ten CMS synthetic claims files in 10,000-row chunks, checking the loaded totals against the source files, transforming in SQL, and comparing the two systems field by field across 4.7 million claim records and 343,803 beneficiary records. It writes 17 analysis files, a report, and a presentation deck. In March I added a nine-tab Streamlit dashboard.

Mostly I directed: what each query had to answer, and how the data should be scored for the Lean Six Sigma calculations. Some of it was hands-on: I started several queries myself and had Claude finish them by following my pattern across about a hundred columns.

03 · Key decisions

Measure it like a process, report it like a decision.

Each field compared is an opportunity for a defect, so data quality comes out as defects per million, yield, and sigma level, field by field and rolled up: 4.58σ for claims and 4.68σ for beneficiaries. Ingestion is validated before anything is compared, so a load error can’t pose as a migration defect.

The scorecard puts the sigma levels beside the counts that matter for go/no-go: 4,777 missing claims, 159 missing beneficiaries, and 82,699 payment discrepancies. A 4.6σ migration still isn’t ready to cut over with claims missing.

04 · What went wrong

The deck needed corrected figures.

Figures in the presentation deck were wrong and were corrected in June, after the original submission. Numbers in a summary deck need the same check against the pipeline’s output as the pipeline itself.

05 · What I’d change

Lead with what blocks the cutover.

A sigma level near 4.6 looks good. The missing claims are what actually decide go/no-go, so they belong first on the page, with the sigma levels as context.

01 · The problem

People want to read the Bible. Most were never taught how.

Abide is a free online discipleship program that teaches inductive Bible study: observe what the text says, interpret it, and apply it. Each lesson has to reach people the way they actually learn, reading, listening, watching, and working through it in a group, and producing all of that by hand would take months per lesson.

02 · The approach

One lesson, more than 40 assets, one source of truth.

Each lesson is one truth taught through many formats, and the finished, audited article is the source everything else is built from. A documented 13-phase production process, written as a set of skills Claude follows, turns it into the rest: the web lesson; a study guide with a quiz, answer key, essay questions, and glossary; a teacher packet with a lecture keyed to the slides; a class handout; a full slide deck and a short teaching deck; our own two-host podcast; an explainer video of about ten minutes; and a LinkedIn article.

Then, for every section of the lesson, seven to ten of them: an illustration that becomes the section’s slide image, the article read aloud in two AI voices, one female and one male, and a section video, so the full lesson plays on YouTube in sections, 31 to 55 minutes end to end. At about eight sections, that is more than 40 published assets per lesson.

The tools split the work. Claude Code writes and checks: the article’s refinement passes, the slide decks, the podcast and narration scripts, the web pages, and the uploads. Gemini draws the illustrations and voices the narration and the podcast. Gemini Notebook narrates the explainer video and drafts the study guide’s quiz and glossary. Every step that touches Scripture pulls it from a translation tool, never from memory, and a script checks every quotation in every written asset before it counts as done. I run the tools Claude can’t, review each step, and audit every page.

The site at bensonacademy.com is Next.js with MDX lessons on Vercel, audio and PDFs on Cloudflare R2, and video on YouTube: 467 commits from March 27 to October 20, 2026. It is now in its Gamma release, after the Beta, with five lessons rebuilt to this standard, including the first lesson of Abide 102. The whole site was redesigned overnight by Claude Opus 5.5, working toward a goal I set before I went to sleep.

03 · Key decisions

A grounded source, a human gate, one config file.

Grounded and reviewed. Generation works from a curated knowledge base, not open-ended prompting, and a mandatory human review gate comes before anything goes live. For teaching Scripture, accuracy isn’t optional.

One source of truth for courses. A single config file defines every course, and a course switches on by itself when its first lesson file appears, with no other code changes.

Built to be found. The site invites AI search crawlers and checks its search data against a saved baseline in automated tests, so a change can’t silently break how lessons appear in search.

04 · What went wrong

Silent failures, made visible.

The first version was a static site; it was rebuilt in Next.js with all media moved to R2. The audio player used to skip a file that wouldn’t load without saying anything; now it pauses and says the file isn’t available. And one lesson shipped with its search data describing the wrong video, caught and fixed in the next release.

05 · What I’d change

An AI coach for practice between meetings.

Next is finishing the Gamma release and more lessons in the second course, and further out an AI Socratic coach grounded only in the Abide library, so practice can happen between group meetings, not only during them.

For anyone who inherits someone else’s large spreadsheet. It turns the workbook into facts, every formula, dependency, pattern, and defect, and those facts feed a Gemini Gem or a Claude skill: living documentation you can ask how the spreadsheet works.

How I evaluate it → What it does for a client →

Triggered
Hand it any spreadsheet. It extracts every formula, dependency, pattern and defect, maps how the tabs connect, and writes the results as reports.
Then ask questions

01 · The problem

Everyone inherits a spreadsheet nobody documented.

It started with an interview take-home: work out how an existing workforce analytics workbook actually worked. But the problem is universal. Anyone who inherits a large spreadsheet has the same questions, and pasting it into an AI chat gets confident answers about formulas and dependencies the AI never really traced. I wanted the answers to start from facts.

02 · The approach

Scripts pull the facts, and the model explains them.

A Python tool opens the workbook from a Google Sheets link or an .xlsx file and parses every formula into its references, functions, and hard-coded numbers. From that it builds the dependency graph between tabs and cells, collapses repeated formulas into patterns, marks each tab as input, calculation, or output, and flags defects in 17 categories, from typed-over formulas to hidden sheets.

It writes four things: a report for a person, a structure-only context file for a Gemini Gem, a DuckDB database, and one JSON file with everything. I built it in one evening: 15 commits on September 11, 2026.

03 · Key decisions

The model sees only structured output.

The working rule is in the README: scripts do the extraction and the deterministic checks, the model only sees structured output, and a person reviews anything that becomes a source of truth. The Gem has to cite a sheet and cell for every claim, and label each answer as found, inferred, or “confirm with the owner.”

Every table and column in the database has a comment, and one view, vw_schema, returns the full data dictionary. An AI assistant is told to query it first, so it orients from the database instead of a pasted summary.

Documentation that answers questions. The structured output becomes the knowledge behind a Gemini Gem or a Claude skill, so anyone can ask what a tab does, what feeds a number, or how a particular formula works, and get an answer with the cell it came from. Unlike a written spec, it’s rebuilt from the workbook on every run.

Practice before real data. The tool generates a deliberately broken workbook with an answer key of 15 planted defects. On its first run the Gem found a sixteenth that nobody planted: the workbook’s own README pointed to the wrong cell. Its 24-question acceptance test includes four trick questions; it answers all 24 with citations and refuses the four traps.

04 · What went wrong

Even the answer key had a defect.

One entry in the practice workbook’s answer key pointed at the wrong month, so a correct finding would have been scored wrong. It took a commit to fix the key itself.

And Gemini Gems don’t re-read a linked Google Doc when it changes, whatever the help text says. After every refresh the Docs have to be removed and attached again, a step now written into the instructions.

05 · What I’d change

Catch the formula that is consistent and wrong.

The biggest known gap: a formula block that is internally consistent but computes the wrong thing looks clean, so the row labels still need a human review. References that run down a column while reading across a row aren’t grouped into patterns yet, and charts only come through from Google Sheets, not .xlsx files.

How I evaluate it →

The code is the source of truth. One command builds the current workbook from the latest code, checks it, and keeps the user guide in step with it.

Triggered: the build
On demand, the generator builds the workbook as an Excel file and as a native Google Sheet. The Excel build is recalculated in real Excel and scanned for error values, and both are checked against a worked example’s 134-value answer key. A new Google Sheet build moves the previous one to Drive trash, so only the current version is live.
Triggered: the user guide
With one flag, a build that passes its checks also regenerates the user guide: tab purposes, columns, dropdowns, conditions, blueprints and commands come from the same model as the workbook, and every tab’s screenshot is retaken from the verified example. Only the explanatory prose is hand-written, and the build stops if a new tab has no place in the guide.
Publishing
One more command mirrors the guide into my profile site, removing pages that no longer exist; I commit and push it.
Releases
Only a verified build is copied into the release folder, and it is the copy Excel saved, so it opens with its values already calculated.

01 · The problem

Change programs prescribe before they diagnose.

Most change programs reach for training before finding where adoption is actually breaking down. I wanted a tool I could bring into any job to apply my ADKAR-aligned approach, the one in my ADKAR article series: find each group’s barrier, confirm it with evidence, find the failing condition, and only then choose an intervention.

Spreadsheet tools also decay. Every engagement modifies its own copy, and the improvements stay stranded in that one file.

02 · The approach

The program is the product.

The method’s content lives in one source file. A Python generator turns it into a platform-neutral workbook model, and two renderers write that model natively as an Excel file and as a Google Sheet: 21 tabs organized by the five FIRST steps, Frame, Isolate, Root, Select, and Track. The same program writes a ten-page user guide, with its screenshots taken from the verified build.

I designed the method and the product beforehand; Claude Code built the generator with me reviewing, in 18 commits over about 14 hours on September 22 and 23, 2026.

03 · Key decisions

Product management, applied to a spreadsheet.

Formulas and design live in the program. Nobody edits a generated workbook by hand. Improve the program once and every future build, in both formats, gets the improvement.

Verified in the real engines. The build opens the Excel file in real Excel, recalculates, and checks for repairs, errors, and circular references; Google computes the Sheet. Both are checked against a 134-item answer key built on a fictional company seeded so every rule fires, and both pass 134 of 134.

Context engineering · In daily use

Keystone: standard work for AI agents

The operating manual every AI tool I use reads before it works. It holds what’s true about me, how each kind of job gets done, and what the tools have learned, across 106 skill files, 100+ purpose-built scripts, and an inventory of every tool the agents can reach. Each task loads a short router and only the pages it needs, about 3% of the whole. Synced every ten minutes between a Windows laptop and a Linux desktop, so work starts on either machine with the same context. Built for one person; designed so a team could copy it.

A peer researcher: an expert method written into AI skills from its textbook, which also found errors in my own lessons.

How I evaluate it →

Keystone keeps itself in sync, and its skills make other automation one request away.

Scheduled: vault sync
Every ten minutes, each machine pulls, commits and pushes the vault. Every change is in Git, so any file can roll back, and both machines start from the same context. Config files that live outside any repo ride along.
On demand
The skill and context system lets one request start a wide range of work: a job package, a lesson asset, an email cleanup. An audit script checks the skills against the standard, and a fact guard confirms a rewording pass dropped no facts.

Why it matters: the automations in the other projects depend on this. Every skill they run lives here.

01 · The problem

Capable tools that start every session from zero.

AI tools are good at the work and forget everything between sessions. Each one knew different things, facts I gave in a chat drifted from the facts I gave in the next, and I kept making the same corrections. It is the tribal-knowledge problem every operation has: the know-how lives in someone’s head, so the work comes out differently every time.

02 · The approach

Standard work, written where the work happens.

I solved it the way process work always has: document the work at the point of use, keep one source of truth, check it, and improve it continuously. Keystone is a private git repository of Markdown files, organized by projects, areas, resources and archive, and every AI tool I use reads it first: Claude Code, Claude Desktop, Gemini and Copilot.

Each layer is small and points to the next. One short instruction file is read every session. An index gives one line per skill, saying when to load it. A router for each domain (job search, Bible study, course production, the machines and tools) sends each kind of request to one reference page. A typical task reads the router and two pages, about 5,400 words of roughly 158,000, instead of everything at once.

Standard work also means the tools are at the station. The environment pages list everything within an agent’s reach (command-line tools, databases, local MCP servers, and each domain’s scripts), so it uses what exists instead of improvising. A scheduled job keeps the vault identical on a Windows laptop and a Linux desktop, so I can start work on either machine and the AI has the same context and instructions.

03 · Key decisions

Facts kept apart, and checked by code.

Ground truth is separate from what the tools learn. Facts about my record live in one place that every procedure points to, never copied into each step, so a correction is made once.

Every file says what AI may do to it: edit freely, only add, or only read. The architecture file and the instruction file are read-only; changes are proposed to me.

Code does the mechanical work; the model does the judgment. The repository holds 100+ deterministic scripts, each built for one job: pulling and verifying Scripture, rendering slides and video, narrating audio, uploading media, exporting resumes. A skill gives the script and how to run it, so the same input gives the same output every time and no tokens are spent on steps code can do.

Scripts also check what Claude writes. An audit script holds every skill to Anthropic’s authoring guidance, and a fact guard fails any rewording pass that drops a number, date or path.

04 · What went wrong

The manual drifted, the way manuals do.

Facts piled up in Claude’s own memory, close to 200 notes, and some disagreed with the vault. The instruction files for three AI tools had been copied by hand and no longer matched, and the architecture document still described the design from six months earlier. An audit found all of it. The fix was structural: one instruction file every tool points to, durable facts moved into the vault with memory reduced to pointers and live state, and an index skill with a check that flags long or orphaned entries.

05 · What I’d change

The same pattern, for a team.

I would start with one router per domain and a single instruction file on day one, instead of growing into them. In a new group I would copy the pattern into a shared repository: playbooks by role and workflow, a named owner for every file, the audit and fact checks running on every change, and new hires and their AI tools reading the same source of truth from their first day.
